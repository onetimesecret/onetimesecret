## Bottom line

The recent full-mode (Rodauth) auth hardening work is well-engineered and fail-secure by design — no defects found in that code itself. However, all of it targets **full mode only**, and the application defaults to **simple mode** (`AuthConfig#mode` in `lib/onetime/auth_config.rb` falls through to `'simple'` for any unset or unrecognized value). Two hardening features that already exist for full mode were never backported to the default mode, reopening one previously-fixed issue. Both have since been backported (see the updates under each finding); the structural lesson stands — a control added behind a Rodauth hook does not exist in the mode most deployments run.

Findings #4 and #5 were added on 2026-07-31 while reviewing #2's fix; both are post-audit and both are now fixed. A third entry filed the same day — an unthrottled `/auth/create-account` clobbering an in-flight password-reset token — was refuted on review and withdrawn; its number (#3) is retired rather than reused, and the slot carries the withdrawal note.

## Findings

### 1. HIGH — Password change/reset does not revoke other sessions in simple (default) mode — **FIXED same-day, see update**

**Files (as of audit time, commit `e6a6e46d`):** `apps/api/account/logic/account/update_password.rb` (`UpdatePassword#perform_update`), `apps/api/account/logic/authentication/reset_password.rb` (`ResetPassword#process`, the `@cust.update_passphrase` call)

When `Onetime.auth_config.full_enabled?` is false (the default), `UpdatePassword#perform_update` calls `cust.update_passphrase!` directly (`lib/onetime/models/features/passphrase_hashing.rb`), and the self-service `ResetPassword` logic calls `@cust.update_passphrase`. Neither path calls a session-revocation operation, and neither writes `Customer#last_password_update` — that field is set *only* by `Auth::Operations::UpdatePasswordMetadata`, invoked solely from the Rodauth `after_change_password`/`after_reset_password` hooks (`apps/web/auth/config/hooks/account.rb`), i.e. full mode only.

Because the field stays 0 for simple-mode customers, `session_predates_credential_change?` (`lib/onetime/application/auth_strategies/helpers.rb`) always short-circuits to `false`, so neither the immediate active-session kill nor the #3810 watermark-based defense-in-depth check ever fires for simple-mode accounts. A stolen/compromised session survives the victim's own password change or reset for the full session TTL (up to 24h).

This was a direct regression of the already-"Fixed" M-2 finding from the 2026-07-06 audit, scoped specifically to the mode most deployments actually run.

**Original recommended fix:** In simple mode, call a session-revocation operation from `UpdatePassword#perform_update` and `ResetPassword#process`, and stamp a credential-change watermark on both paths.

**Update — resolved:** PR #3949 (commit `2793e644`, "revoke sessions on password change/reset in simple mode") shipped the fix the same day this report was opened, landing on `main` before this report's own PR merged. It added `Onetime::Logic::CredentialChangeSessionRevocation` (`lib/onetime/logic/credential_change_session_revocation.rb`), included into both logic classes: `ResetPassword#process` now calls `revoke_sessions_for_credential_change(@cust)` (all sessions revoked — the requester is unauthenticated), and `UpdatePassword#perform_update` calls `revoke_other_sessions_simple_mode`, which revokes every *other* session while rotating and re-stamping the caller's own session past the new watermark. The shared module stamps the watermark itself via `customer.last_password_update!` in `stamp_credential_watermark`, closing the missing-watermark half of the finding. Re-verified against current source at commit `ca48bd19` (2026-07-31); this finding is closed.

### 2. MEDIUM — No rate limiting on `/auth/reset-password-request` in simple (default) mode — **parity gap FIXED; residuals below**

**File:** `apps/api/account/logic/authentication/reset_password_request.rb`, routed via `apps/web/core/routes.txt` → `Core::Controllers::Registration#request_reset_email`

Issue #3872 (commits `ab81d3d`/`930ce71`) added a per-IP + per-target rate limiter (`Onetime::Security::ResetRequestRateLimiter`), but it's wired only into `apps/web/auth/config/hooks/reset_password_request.rb`, loaded solely when `full_enabled?` (`lib/onetime/application/registry.rb` skips `web/auth/` otherwise). The simple-mode logic class has no limiter call at all. `ResetPasswordRequest#process` already returns identical responses for existing/non-existing accounts (good), but with no throughput cap an attacker can mail-bomb arbitrary addresses and accumulate unlimited samples against the residual timing side-channel already documented at the top of that file. Same root cause and parity gap as finding #1.

**Original recommended fix:** Add the same `ResetRequestRateLimiter` check (keyed the same way) into the simple-mode path.

**Update — parity gap resolved:** `AccountAPI::Logic::Authentication::ResetPasswordRequest` now includes `Onetime::Security::ResetRequestRateLimiter` and calls `enforce_reset_request_rate_limit!(reset_request_client_ip, @login_or_email)` as the FIRST statement of `#raise_concerns` — ahead of the `valid_email?` format check and ahead of the `Onetime::Customer.find_by_email` lookup in `#process`, matching the full-mode hook's before-the-route-body ordering. The per-IP subject is the strategy-metadata client IP (`AuthStrategies::Helpers#client_ip` → `env['otto.client_ip']`, the trusted-proxy-resolved and privacy-masked value the hook also reads). The per-login subject is the sanitized login actually used for the lookup — deliberately not byte-identical to the hook's raw param, since each mode keys on the string *it* resolves accounts with, which is what keeps the backstop bucket 1:1 with that mode's lookup; the divergence only merges submissions into one bucket, never splits a target across several. No new enumeration oracle is introduced: the limiter keys only on request-observable inputs. `Onetime::LimitExceeded` is not an `OT::FormError`, so it bypasses the controller's form-error rescue and reaches the Otto handler registered in `lib/onetime/application/otto_hooks.rb`, rendering the ADR-013 429 with `retry_after`. Covered by `spec/integration/simple/reset_password_request_rate_limit_spec.rb` (real HTTP through the mounted Core app: per-IP tier keyed on the masked client IP with per-source isolation, per-login backstop, 429 enumeration symmetry, no lookup/dispatch once locked, and the shipped no-config default being ON) and unit coverage in `apps/api/account/spec/logic/authentication/reset_password_request_spec.rb`. The parity gap is closed.

The adjacent unauthenticated route `POST /auth/create-account`, flagged at fix time as a comparable gap, was reviewed separately and is covered by findings #3–#5 below.

**Residuals — noted at fix time; two since closed (see each item):**

1. **Per-IP attribution is only as sound as the edge's forwarded-header handling.** Both modes key on `env['otto.client_ip']`, the trusted-proxy-resolved value, and the same value feeds `LoginRateLimiter`, `IncomingRateLimiter`, ban checks and audit-log IP attribution — so a deployment whose edge or `site.network.trusted_proxy` configuration lets clients influence that resolution weakens all of those controls at once, not just this limiter. **Mitigation is deployment-side:** align the `trusted_proxy` settings with how your edge actually emits forwarded headers. The operator guidance in `etc/defaults/config.defaults.yaml` was corrected as part of this work — its previous description of `filter` mode did not match Otto's actual resolution behavior — and is the reference for choosing between the modes.
2. ~~The 429 sets no `Retry-After` HTTP header; `retry_after` appears in the JSON body only. Well-behaved clients and proxies read the header.~~ **FIXED (2026-07-31).** Every 429 now carries `Retry-After` (delay-seconds, RFC 9110 §10.2.3). The fix is at the shared HTTP edge, not in this limiter: `Onetime::Application::ErrorCorrelation.apply` — the one helper *both* routing stacks already call when building a typed error body — stashes the body's `retry_after` into `env['otto.retry_after']`, and the new `Onetime::Middleware::RetryAfterHeader` (mounted once in the universal `MiddlewareStack`, so it wraps the Otto apps and the Roda `/auth` app alike) turns it into the header. It had to be a middleware: Otto's `register_error_handler` blocks return a body Hash and nothing else — `Otto::Core::ErrorHandler` builds the header hash after the block returns — so neither stack can set a response header where it builds the body. Because the stash is keyed off the body field rather than the exception, this covers **every** limiter that raises `LimitExceeded` (Reset/Login/Incoming/InviteToken/Passphrase/Feedback/Dns), all of which shared the gap. The header is never overwritten, so the two routes that already set it inline (`link_sso.rb`, `sso_link_confirm.rb`) keep their own value. Scope is 429 **and** 503: `Billing::CircuitOpenError` is registered at 503 and stashes `retry_after` the same way (`OttoHooks`, whose own comment names the un-settable header as the reason the delay is body-only), and `Retry-After` is legal on 503; 3xx is excluded because nothing produces one. The seconds value is rounded **up**, never truncated, so the header can never advertise a shorter back-off than the body states. Coverage: `spec/unit/onetime/middleware/retry_after_header_spec.rb`, the stash cases in `spec/unit/onetime/application/error_correlation_spec.rb`, and an end-to-end assertion in **both** mode lanes (`spec/integration/simple/…` and `apps/web/auth/spec/integration/full/…`) so the two stacks cannot drift.
3. ~~A throttle writes no audit-log record — only an `OT.le` line (`[ResetRequestRateLimiter] … hit cap`). There is no queryable signal for a reset-request enumeration attempt.~~ **FIXED (2026-07-31).** A cap-hit now also writes one `Onetime::AdminAuditEvent` (`verb: auth.reset_request_throttled`, `actor: anonymous`, `result: failure`, `target: "<tier>:<obscured subject>"`, detail carrying tier/count/max_attempts/window/lockout), which is the codebase's single queryable audit store — readable via `GET /api/colonel/audit` and the CLI. Same call shape as the simple-mode `colonel.signin` write in `Core::Logic::Authentication::AuthenticateSession`, and best-effort in the same way. Two constraints shaped it: (a) the target is the **obscured** subject (`/16` for IPv4, `obscure_email` for logins) — the audit trail must not become the enumeration oracle the limiter exists to bound; (b) it records **only on the cap-reaching request, never on the deny path**. `AdminAuditEvent` is capped by *count* with no TTL, so its write rate must never be something an unauthenticated caller can drive per-request (see the cap rationale on the model and on `Onetime::AuditedFailure`). Cap-hit-only bounds writes to one per bucket per lockout window (1h default), so minting another event costs a full cap's worth of requests against another subject. Because this is the first unauthenticated writer into that store, the `MAX_EVENTS` rationale on `Onetime::AdminAuditEvent` — which asserted that *every* write is authenticated colonel activity — was rewritten to state the actual invariant (authenticated **or** rate-limited below a frequency an attacker can drive), to name this writer as the sole exception, and to require that any future unauthenticated-triggerable verb carry a comparable per-window bound or move to its own collection; `AuditedFailure.authorization_rejection?` gained the matching note that it bars `LimitExceeded` by inheritance from `Forbidden`. **This does not eliminate the exposure**: a distributed attacker — or any deployment where residual 1's client-IP attribution is weak — can still mint buckets cheaply, and operators relying on the admin trail should pair this with residual 1's deployment-side mitigation. Scope: the reset-request limiter only — the sibling limiters share the gap, but each needs its own verb and its own eviction analysis, so none were changed. Coverage: `try/unit/security/reset_request_rate_limiter_try.rb` (including an explicit "denied requests write no further events" case) and the `audit trail` group in `spec/integration/simple/reset_password_request_rate_limit_spec.rb`.
4. A non-JSON client (browser form, JS disabled) gets a raw JSON 429 document rather than the redirect-with-flash an `OT::FormError` gets on the same route. Same shape as the pre-existing `AuthenticateSession`/`LoginRateLimiter` path; the shipped frontend posts JSON (`src/shared/composables/useAuth.ts`), so no live user path is affected.
5. The per-login tier is a targeted-DoS primitive by construction: enough requests for one address lock that address's reset flow for the lockout window from any source IP. This is deliberate and reasoned about in the `ResetRequestRateLimiter` docstring — the per-login cap is the *looser* tier precisely to keep this expensive — but wiring simple mode newly exposes default deployments to it.

Residuals 2–4 belong in the limiter / shared HTTP edge rather than in either call site. 2 and 3 were closed there on 2026-07-31 (see each item); 4 is unchanged.

**Operational note:** the limiter defaults to enabled (`enabled` is only disabled by a literal `false`), so simple-mode deployments begin throttling at 10 requests/IP/hour on upgrade. The per-IP subject is the privacy-masked network (`/24`, `/48`) and the lockout runs the full configured hour from the cap-hitting request regardless of where in the window it falls, so a single office NAT or one hostile host in the same masked range can 429 that neighborhood's reset requests for an hour. `RESET_REQUEST_RATE_LIMIT_ENABLED=false` opts out; `RESET_REQUEST_RATE_LIMIT_MAX_PER_IP` raises the cap for dense-NAT populations. Redis errors propagate fail-closed — note this is a change of *failure point*, not a new dependency: `#process` already calls `Onetime::Customer.find_by_email` and the request already carries a Redis-backed session, so simple-mode reset was already non-functional during a Valkey outage.

### 3. WITHDRAWN (filed and refuted 2026-07-31) — reset-token clobbering via unthrottled `/auth/create-account`

**This slot is retired, not reused.** An earlier revision of this report briefly published a different finding under this number, and an unrelated one under it after that. Any external reference minted against either — a PR comment, an issue, a tracker entry citing "audit 2026-07-30 finding #3" — resolves here. Nothing has been renumbered into this slot: the two entries that came out of the 2026-07-31 review are **#4** and **#5** below.

**Refuted.** As first filed this entry claimed that unthrottled `/auth/create-account` posts could overwrite an in-flight password-reset token via `send_verification_email` and lock a victim out of the reset flow. The exploit chain fails at the first link and would still fail at two further independent points:

1. **Nothing writes `reset_secret` from this path.** `send_verification_email` was unreachable from `CreateAccount` (the dead branch in finding #5, since fixed), so the `reset_secret` write inside `Onetime::Logic::Base#send_verification_email` never executes here. The filed text was internally contradictory: it claimed the code takes the silent-success branch *and* calls `send_verification_email` — those are the two arms of one `if`.
2. **An unverified account never holds a reset token to clobber.** `ResetPasswordRequest#process` short-circuits `cust.pending?` into `send_verification_email(customer: cust)` + return; the `Onetime::Secret.create!` and `cust.reset_secret = …` writes later in that method are reached only for non-pending customers. The victim state the finding required cannot exist.
3. **Pending accounts are rejected at redemption anyway.** `ResetPassword#process` raises `'Account not verified'` after `valid_reset_secret!` has already succeeded.

**The refutation survives finding #5's fix — this stays closed now that #5 is applied.** Link 1 *was* contingent on the #5 bug: the `verified?` fix makes `send_verification_email` reachable from `CreateAccount` again for unverified accounts, which removes link 1. Links 2 and 3 are not contingent and each is independently fatal to the chain. Specifically, `pending?` (`lib/onetime/models/customer/features/status.rb`) is defined on the **predicate** `verified?`, not on the raw field, so it was unaffected by the #5 bug: an unverified customer always takes the `send_verification_email`-and-return branch in `ResetPasswordRequest#process` and never reaches the `reset_secret` write. There is no victim state, before or after the #5 fix. (The resend path that #5's fix reopened is additionally bounded by the verification-resend cooldown shipped with it — see #5's update.)

Also wrong as filed: the code cited for the silent-success claim was the `password_too_short` error branch, not the branch in question; "in either auth mode" (that logic class is simple-mode-only — see #5); and "mail-bomb it without limit" — repeat POSTs for an *existing* address sent zero email as of the audit snapshot (post-#5-fix, at most one resend per cooldown window). Reproduced against the real simple-mode rack stack: N repeat POSTs to one address → 200 each, 0 additional mails, `reset_secret` bit-identical; N POSTs to N distinct addresses → N accounts + N welcome mails. What survives from the filed entry is the missing rate limit, refiled at its true severity as finding #4 (since fixed).

### 4. LOW (new, 2026-07-31) — no rate limit on unauthenticated account creation — **FIXED, see update**

**File:** `apps/api/account/logic/account/create_account.rb`, routed via `apps/web/core/routes.txt` (`POST /auth/create-account … auth=noauth`) → `Core::Controllers::Registration#create_account`

As filed, `CreateAccount` enforced no rate limit of any kind — neither in the logic class nor in `Core::Controllers::Registration`. The reachable primitive is unauthenticated, unthrottled **account creation**: one Customer record plus one welcome email per *distinct* address, with subaddressing (`victim+N@…`) collapsing many addresses onto one mailbox. Impact is datastore growth (no TTL on the Customer hash) and unsolicited mail.

LOW, not medium: no auth bypass, no data exposure, and no denial of an existing user's account — repeat posts against an address that already exists send nothing at all (finding #5). This is spam/resource abuse, not reset-flow denial.

Adjacent dead control: the `skill` honeypot field is captured in `CreateAccount#process_params` and never read anywhere.

**Fix (as filed):** apply a per-IP limiter to the `CreateAccount` entry path on the same shape as `ResetRequestRateLimiter`.

**Update — resolved:** PR #3963 (merged 2026-08-01) added `Onetime::Security::CreateAccountRateLimiter`, enforced at the top of `CreateAccount#raise_concerns` before any datastore touch. It is a single per-IP tier by design — the abuse pattern mints a fresh address per request, so a per-target tier has no stable subject to key on; the source IP is the only one. Registered as `create_account_ip` in the ratelimit registry with its own config surface. Full mode is covered too: the Rodauth `before_create_account_route` hook (`apps/web/auth/config/hooks/create_account.rb`) applies the same limiter, so neither mode is the softer target. Incidental fix in the same PR: this logic class was the only site reading strategy metadata with the string key `'ip'` where `build_metadata` uses symbols, so the `[new-customer]` log line always carried a blank IP. Coverage: unit tryouts for the limiter plus integration examples across both modes. This finding is closed.

### 5. LOW–MEDIUM, functional not security (new, 2026-07-31) — dead verification-resend branch in `CreateAccount` blocks legitimate account recovery — **FIXED, see update**

**File:** `apps/api/account/logic/account/create_account.rb` (`CreateAccount#process`, the existing-account branch), routed via `apps/web/core/routes.txt` (`POST /auth/create-account … auth=noauth`) → `Core::Controllers::Registration#create_account`. Simple mode only: `Auth::Application` mounts at `/auth` and loads only in full mode (`apps/web/auth/application.rb`; `lib/onetime/application/registry.rb`), and the registry sorts mounts longest-prefix-first, so in full mode this route is Rodauth's.

The existing-account arm tests the RAW field — `if @cust.verified` — instead of the predicate `verified?`. `verified` is declared `base.boolean_field :verified` (`lib/onetime/models/customer/features/status.rb`), and `Onetime::FieldTypes::BooleanFieldType` canonicalizes to the STRING `'true'`/`'false'` on write, on serialize and on deserialize. `"false"` is truthy in Ruby, so *every* persisted customer — verified or not — takes the silent-success branch, and the `send_verification_email` call in the other arm is unreachable. The model documents the canonical stored form in `status.rb`, which is exactly why `verified?` is a string-equality check.

Impact: a user whose first verification email was lost can never get it resent by re-submitting signup. They are told "Check your email for verification" and nothing is sent — contradicting the behavior table documented atop `Core::Controllers::Registration` ("No-autoverify + existing unverified → Yes (resent)"). The unit spec masks the bug: `apps/api/account/spec/logic/account/create_account_spec.rb` stubs `verified: false`/`verified: true` as real Ruby booleans, values the model never returns.

**Fix (as filed):** the check should read `if @cust.verified?`. Sweep for the same raw-`boolean_field` truthiness class of bug elsewhere (`if cust.verified`, `if cust.suspended`). Applying it does **not** reopen finding #3 — see the contingency note there.

**Update — resolved:** PR #3955 switched the check to the `verified?` predicate (commit `9317b8af`) and re-stubbed the unit spec with the canonical persisted string forms, guarded so raw-boolean stubs cannot mask this class of bug again. Because the fix makes the resend branch reachable, the same change-set added `Onetime::Security::VerificationResendCooldown` (commit `676163e3`): duplicate signups for an existing unverified account resend at most once per cooldown window, so the newly-live resend path is bounded independently of finding #4's per-IP cap. This finding is closed.

Narrow residual, not a finding: a legacy record with `verified` genuinely `nil` **and** `role != 'customer'` would fall through to the resend branch, but simple mode always writes `cust.verified` before `save`, so that state is not reachable through normal flows.
