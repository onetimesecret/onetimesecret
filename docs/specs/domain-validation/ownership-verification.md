# Domain ownership and verification lifecycle

This reference distinguishes the ownership flag from the derived domain lifecycle
and describes the transition from the legacy `verified` storage field.

## Terms

- **`txt_validation_value`** is an expected challenge generated by the application.
  Its presence does not establish that a TXT record exists in DNS.
- **`ownership_verified`** records whether the validation strategy accepts domain
  ownership. DNS validation and an operator override can set it. The passthrough
  strategy accepts ownership by operator policy without checking a TXT record.
- **`resolving`** records whether the active strategy reports the domain as resolving.
  It does not establish ownership.
- **`verification_state`** is a derived lifecycle label, not another ownership check.

The implementation is in [CustomDomain](../../../lib/onetime/models/custom_domain.rb).
It evaluates already-loaded fields without a DNS lookup:

| Generated challenge | Resolving | Ownership verified | Lifecycle label |
| --- | --- | --- | --- |
| No | Either | Either | Unverified |
| Yes | No | Either | Pending |
| Yes | Yes | No | Resolving |
| Yes | Yes | Yes | Verified |

A domain can therefore have **Ownership verified: Yes** and
**Verification: Pending**. `ready?` is true only for the Verified lifecycle state.

## Storage compatibility

`ownership_verified` is the canonical native boolean field. Its accessor falls
back to the loaded legacy `verified` value only when the canonical value is nil
or absent. Explicit canonical `false` takes precedence over legacy `true`.

Nil means unset, not revoked. Write `false` to revoke ownership verification;
clearing the canonical field to nil can expose an older legacy value again.

The legacy storage field remains readable but is excluded from full saves.
Full saves write the effective ownership value under `ownership_verified`.
The compatibility methods `verified`, `verified=`, and `verified!` remain;
the setters and `save_fields(:verified)` target canonical storage. Bare bang
reads use Familia's raw canonical-field read, not the effective getter fallback.
Use `ownership_verified` for effective reads.

CustomDomain's `safe_dump` includes `ownership_verified` and retains `verified`
as an ownership-only API alias. Existing hand-built API responses and request
parameters retain their `verified` spelling; this change does not remove them.
The confirmation timestamps and operator provenance fields retain their names:
`verified_confirmed_at`, `verified_unconfirmed_since`, and `verified_by_override`.

## Operator rollout and backfill

**Prerequisite:** stop legacy writers before enabling canonical writes or running
backfill. This includes old application processes, maintenance jobs, and console
scripts that write only `verified`. An old process can otherwise write
`verified=false` after `ownership_verified=true` exists, and the new reader will
continue to prefer the canonical true value. Read fallback does not synchronize
two concurrently written fields.

After the writer cutover, use the registered housekeeping chore:

```console
bin/ots housekeeping run Onetime::CustomDomain migrate_ownership_verified
```

The [chore](../../../lib/onetime/models/custom_domain/chores/migrate_ownership_verified.rb)
atomically copies the legacy bytes only when the new field is absent. It:

- copies both true and false, including legacy encodings;
- does not overwrite any existing canonical field, including false;
- skips records without a legacy field;
- leaves the legacy field and unrelated data untouched;
- does not recreate records deleted before the script runs;
- reports a modification only when a field was copied.

There is no dry-run mode. The command performs writes and requires datastore
access, including permission to execute Lua scripts. The same chore can also run
through scheduled housekeeping when CustomDomain is included. Repeating the
chore should report zero modifications once all reachable domains are copied.
Datastore exceptions are counted by the housekeeping runner and can be retried.

**Rollback limit:** preserving legacy bytes does not keep them current. Returning
to an old binary after canonical writes can expose stale ownership state. A
rollback requires reconciliation from the canonical field before old writers
resume; this chore does not perform reverse migration or delete legacy fields.

## Proposed Familia support

Familia **2.12.0**, the version in this checkout's lockfile, has no built-in
`read_fields:` or `copy_from:` implementation. The local compatibility field uses
the existing `FieldType#persistent?` and mapped-accessor extension points.
No dependency change or upstream patch is included here.

A reusable upstream feature would fit better as an ordered read-alias option:

```ruby
# Proposal, not a supported Familia 2.12.0 option:
boolean_field :ownership_verified,
  storage: :native,
  read_fields: [:ownership_verified, :verified]
```

Proposed semantics:

1. Resolve aliases during shared model hydration, including bulk loads and refresh.
2. Preserve canonical false; resolve aliases before applying field defaults.
3. Pass the selected value through the canonical field's coercion.
4. Specify whether nil counts as unset; the local adapter treats it that way.
5. Persist only the canonical name. Reads must not trigger datastore writes.
6. Define raw bang reads, partial saves, and batch-writing behavior explicitly.

`copy_from:` is less clear because it could imply persistence during a read.
Keep backfill as an explicit operation even if read aliases move upstream.
Generic read aliases would remove the local compatibility adapter, but would not
remove the need to coordinate old and new writers.
