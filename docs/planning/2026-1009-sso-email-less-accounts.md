# SSO email-less accounts: Phase 2 proposal

**Status: PROPOSED — not implemented.** Date: 2026-10-09. Design for G2 approval: [account-model-design](../specs/sso-email-less-accounts/account-model-design.md) and [ADR-051](../adr/adr-051-account-login-is-not-the-contact-email.md) (2026-10-10).

Scope: followup item 3 from [#3478](https://github.com/onetimesecret/onetimesecret/issues/3478), revising the Phase 2 direction in [#3499](https://github.com/onetimesecret/onetimesecret/issues/3499). Followup item 1 is the [operator guide](../authentication/per-install-sso.md). Approval to document this proposal is not approval to implement it or widen tenant access.

Goal: allow a validated SSO identity to provision an account when no usable email claim is supplied, without treating email or a username as the identity. Missing claims do not prove absence of a mailbox. Graph enrichment, new claim fallbacks, and changes to tenant authorization or trusted-linking policy are outside this proposal.

## Current baseline and corrections

Baseline inspected: main-derived `fix/3478-followup`, HEAD `3a6d2d1a74238b5e24250a887bc34f03034e59f0`, including its uncommitted missing-email guards. Source observations below are not implemented Phase 2 behavior.

| Constraint | Implementation evidence |
|------------|-------------------------|
| Email is the login column | [base.rb:67](../../apps/web/auth/config/base.rb#L67): `auth.login_column :email`; login normalization also assumes email. |
| SQL requires email | [001_initial.rb:26–35](../../apps/web/auth/migrations/001_initial.rb#L26): `citext :email, null: false`, PostgreSQL `valid_email` CHECK, and unique email index (active statuses where partial indexes are supported); SQLite also requires non-null email. |
| Customer creation and lookup require email | [ensure_customer_for_account.rb:85–127](../../apps/web/auth/operations/ensure_customer_for_account.rb#L85) finds/creates by normalized email, then stores `customer.extid` in SQL `external_id`. |
| Redis has two unique email indexes | [customer.rb:187–190](../../lib/onetime/models/customer.rb#L187): `unique_index :email, :email_index` globally and `unique_index :email, :email_index, within: Onetime::Organization`; [create!:430–444](../../lib/onetime/models/customer.rb#L430) raises `'email is required'` for empty email. |
| Identity is already issuer-scoped | [migration 008](../../apps/web/auth/migrations/008_issuer_scoped_identities.rb#L82) adds `[:provider, :issuer, :uid]` uniqueness. Existing rows and ownership must survive Phase 2. |

The current [creation guard](../../apps/web/auth/config/hooks/omniauth.rb) redirects absent/blank email to `missing_email`, malformed email to `invalid_email`, and signup policy rejection to `domain_not_allowed`. Platform linked-identity sign-in and authorized authenticated Connect can omit callback email; this does not permit email-less account creation. A nonempty [tenant allowlist](../../apps/web/auth/config/hooks/omniauth_tenant.rb#L669) still rejects missing email for returning identities and Connect. Missing/corrupt tenant policy stays fail-closed.

**Correct #3499's trust ranking, not just its fallback order.** `info.email` and `raw_info.mail` are not universally verified mailbox claims. Claim presence, structural validity, deliverability, mailbox-control evidence, and authority to link an account are separate facts. `upn` and `preferred_username` are mutable hints, not substitutes. An absent `mail` claim does not establish that a user has no mailbox.

Primary wording:

- [Microsoft ID token claims reference, `email`](https://learn.microsoft.com/en-us/entra/identity-platform/id-token-claims-reference#payload-claims): "This value isn't guaranteed to be correct and is mutable over time. Never use it for authorization or to save data for a user."
- [OIDC Core 1.0 §5.1](https://openid.net/specs/openid-connect-core-1_0.html#StandardClaims) defines `email_verified: true` as meaning the provider "took affirmative steps to ensure that this e-mail address was controlled by the End-User at the time the verification was performed." This is a provider assertion within its trust framework, not an unconditional guarantee of current control or permission to link accounts.
- [Microsoft optional claims reference](https://learn.microsoft.com/en-us/entra/identity-platform/optional-claims-reference#v10-and-v20-optional-claims-set) defines `xms_edov` as a "Boolean value indicating whether the user's email domain owner has been verified." It is not mailbox-control proof.

The [Entra definition](../../lib/onetime/sso_provider/entra.rb) already requests `openid profile email` and uses the gem's stable default `tid` + `oid` UID. [Native strategy 3.1.1](https://github.com/pond/omniauth-entra-id/blob/7a45b1f4aadefd2d19781c80acc5fd17251e21db/lib/omniauth/strategies/entra_id.rb#L94-L204) reads token claims, not directory `mail`; OTS performs no Graph enrichment. [#3965](https://github.com/onetimesecret/onetimesecret/pull/3965) targets `develop`, is absent here, and its `raw_info.mail` fallback cannot supply `mail` absent from native tokens. The [operator caveat](../authentication/per-install-sso.md#entra-email-claims-and-mailbox-verification) covers scopes, optional claims, and UserInfo limitations.

## Proposed identity and data changes

1. **Preserve external identity ownership.** Keep the complete `(provider, issuer, uid)` tuple and all existing rows; retain issuer validation, platform-only legacy backfill rules, and tenant refusal of issuerless providers. Do not replace Entra's default `tid` + `oid` with email, UPN, or a new UID scheme. An OIDC `sub` scoped to its validated issuer is a valid stable identifier. [OIDC Core §5.7](https://openid.net/specs/openid-connect-core-1_0.html#ClaimStability) states: "the only guaranteed unique identifier for a given End-User is the combination of the `iss` Claim and the `sub` Claim." That is protocol guidance, not permission to re-key existing OTS rows. Never create a synthetic `{provider}:{uid}` login that drops issuer scope.
2. **Separate account, login, contact, and verification.** Retain the immutable internal SQL account ID and assign an opaque, unique internal login independent of mutable contact data. Store optional contact email separately with explicit verification state/provenance. Preserve existing email-based local sign-in through explicit resolution; changing contact email must not change internal identity, re-link an SSO identity, or silently adopt a different account. Specify handling of address changes/reassignment and re-verification before using the new contact for recovery.
3. **Migrate SQL and Rodauth together.** Add/backfill a unique, non-null immutable `login`; make contact email nullable while retaining structural validation and the existing active-account uniqueness policy for present addresses. Verify CHECK and unique-index NULL behavior on PostgreSQL and SQLite. Following [Rodauth's non-email login guide](https://rodauth.jeremyevans.net/rdoc/files/doc/guides/alternative_login_rdoc.html), propose `login_column :login` and `email_to { account[:email] }`. Audit login validation, normalization, lookup, SSO account construction, and every email-sending feature; do not keep email-only normalization for opaque logins or case-fold issuer/UID values. These configuration changes alone do not make missing-email flows safe.
4. **Migrate Redis and the SQL–Customer join together.** Change Customer creation/required fields and both global and organization-scoped unique email indexes. An absent contact creates **no email-index entry**: no shared null/empty key, synthetic mailbox, or placeholder address. Present-address add/change/remove operations must reconcile both index scopes without stealing another Customer's entry. Resolve the durable account–Customer association via SQL `external_id` and Customer `extid`, never by email on login or crash retry. Specify how that association is reserved and recovered before any new provisioning writes.
5. **Make cross-store provisioning recoverable.** SQL, identity binding, Redis Customer/index writes, workspace creation, and session setup do not share one transaction. Define durable provisioning checkpoints, concurrency ownership, and idempotent retries for every crash boundary before enabling this path. A retry must resume the same account/Customer/workspace, detect conflicts, and avoid an email-based merge. Migration backfills and reconciliation must also be restartable and idempotent.

## Lifecycle and tenant decisions

All items below are proposed requirements, not new permissions:

- **Tenant access:** a nonempty `SsoConfig.allowed_domains` continues to deny callbacks without a usable email, including linked returning accounts and Connect. Missing or corrupt `SsoConfig` must not become unrestricted. Any alternative authorization (for example, an explicitly approved assignment or immutable membership rule) requires a separate security/product decision and explicit operator approval. Do not switch off allowlists for returning accounts.
- **Recovery and authenticators:** decide how an email-less account recovers from loss of its IdP, enrolls/changes MFA and local credentials, links/unlinks identities, and avoids losing its last usable authenticator. An optional, user-supplied mailbox needs its own verification before mailbox-based recovery; SSO success alone must not satisfy local Connect reauthentication.
- **Contact-dependent operations:** define absent/unverified-email behavior for password resets, magic links, account/contact verification, MFA recovery, billing contact, organization invitations, and notifications. Required operations need a supported non-email path or an explicit unavailable outcome; do not send to opaque login identifiers. Ownership and membership must not be inferred from a reused address.
- **Secret sharing:** test ordinary creation and link sharing without contact email. The recipient-email delivery restriction proposed in #3499 is a separate product decision: neither automatically broaden delivery nor declare it newly supported. Sender display/reply-to behavior and abuse risks need a decision before changing the existing restriction.
- **Cutover/rollback:** use an expand/backfill/compatibility/deploy/enable sequence with verified SQL–Redis reconciliation. Do not enable null-email writes while any web process, worker, CLI, or migration reader still requires email. Define the mixed-version compatibility matrix and rollback boundary. After null-email records exist, rolling back to email-required binaries/schema needs a tested compatible path; no destructive downgrade, fabricated emails, or account deletion to make rollback pass.

## Review and release gates

- **G1 — evidence:** with user/operator consent, inspect real failing claim presence and shape, account type, route, and provider/gem versions. Publish only sanitized observations; no tokens, full/raw auth hashes, private claims, or personal identifiers in GitHub. Use synthetic fixtures derived from that shape, not copied payloads.
- **G2 — design/cutover:** approve the SQL constraints, both Redis indexes, durable association and crash-retry protocol, lifecycle outcomes, migration idempotence, mixed-version plan, and rollback evidence before implementation is enabled.
- **G3 — immediate, separate security review:** review current automatic verification (including absent `email_verified`), trusted-email linking, and email-domain authorization against provider-specific guarantees **now**, independently of Phase 2 delivery. Establish concrete scenarios, explicit risk disposition, and any separately approved remediation. Documenting current behavior does not declare it safe or justify waiting for the larger schema change. This document does not change those policies or claim review sign-off.

## Acceptance evidence required before release

- Cross-tenant isolation: the same synthetic `oid` under two Entra tenants and the same OIDC `sub` under two issuers resolve to distinct full tuples; include an `ignore_tid: true` case. Existing default Entra UIDs, issuer-scoped rows, and account ownership remain unchanged.
- Mutable claims: changed email, UPN, or `preferred_username` never re-link identity or change internal login/account ownership. A username matching a victim's email, address reassignment, and contact-email collision never adopt the victim's account; contact changes reverify and reconcile SQL and both Redis index scopes.
- Null-email persistence/operations: PostgreSQL and SQLite account creation, Redis save/load and global/per-org indexes, session round-trip, login/logout, workspace membership, secret creation/link sharing, API/CLI administration, and contact-dependent outcomes. Multiple null-email accounts must not collide; no shared empty index or synthetic mailbox.
- Tenant returning users: allowed email succeeds; removed/disallowed domain, missing/malformed email with nonempty allowlist, and missing/corrupt configuration deny even an already-linked identity. The deliberately empty allowlist case retains current behavior without bypassing other gates. Assert Connect's reauth/surface/membership/ownership refusals as well as success.
- Provisioning/migration: concurrent first logins, injected crashes at each SQL/Redis/session boundary, retries, repeated/backfill-interrupted migrations, reconciliation, and mixed-version cutover/rollback preserve account–Customer association, identity ownership, and index consistency without duplicate accounts or workspaces.
- Lifecycle: recovery with and without verified optional contact, IdP loss, MFA, last-authenticator protection, email change/removal/reassignment, billing, invites, notifications, and unchanged recipient restrictions have explicit supported or refused outcomes.
- Real Entra route: exercise `/auth/sso/entra` and its callback through the actual strategy and Rodauth, using representative sanitized claim shapes; mocked hooks alone or an all-skipped provider suite are not acceptance evidence. Record versions, executed assertion counts, and separately identified skips; complete an operator-approved live smoke test without publishing credentials or tokens.

This proposal does not implement Phase 2. The accompanying missing-email errors and whitespace regression fix do not enable email-less account creation.
