## 6. Operator callouts for the Deployment Notes

Drafted from PR bodies and fragments. Verify each against the merged tree
before publishing.

- Colonel, admin and staff accounts need mailbox-proof provenance (#4754). Run
  `bin/ots customers doctor --all` before deploying (without `--all` it
  prints usage and scans nothing); re-verify affected accounts with
  `bin/ots customers verify EMAIL`.
- Tenant SSO creates accounts only for addresses inside a custom domain the
  organisation has TXT-verified (#4755). Tenants whose users sign in with
  another domain add and verify it first. Existing accounts keep signing in.
  On TXT-strategy installs a domain counts only with a recorded TXT pass: run
  `bin/ots domains verify --all` after deploying (or wait for
  `DomainRefreshJob`).
- `SMTP_AUTH` is honored for SMTP delivery (#4890). `SMTP_AUTH=login` moves
  from PLAIN to LOGIN, and an unrecognized value with SMTP credentials set is
  a configuration error instead of a fallback to PLAIN. Check it before
  upgrading. With #4908 (merged 2026-11-05) a mail backend that cannot be
  built from its configuration (no SMTP host, an unsupported `SMTP_AUTH`)
  no longer sends the message to the DLQ, where the consumer discards
  non-auth mail: the worker logs `Mail configuration error (provider: smtp):
  ...`, releases its idempotency claim, keeps the message back 15 seconds and
  requeues it, and the delayed mail goes out once a worker starts with a
  working configuration (late, so secret links in it may have expired).
  While the configuration is broken `email.message.send` grows at the send
  rate (it has no TTL), a DLQ-depth alert does not fire, and each cycle logs
  one error line per worker thread. At boot, `CheckEmailerConfig` logs
  `Mail configuration error, email cannot be sent` without stopping the
  site.
- A customer record recreated at login (a Rodauth account with no matching
  Customer) is provisioned with a `verified_by` derived from auth state only,
  `sso` or `legacy`, and neither is mailbox proof, so a recovered customer
  cannot use a system role until an operator verifies the address (#4892).
  `verified_by` tags are validated against
  `Onetime::Customer::VERIFIED_BY_VALUES`; an unknown tag raises before any
  write. The doctor reports a recovered customer left unverified while its
  auth account is Verified (MEDIUM, never auto-repaired).
- API request handling (#4871, merged 2026-11-08). Malformed query, JSON or
  form input to `/api/v2`, `/api/v3` and `/api/incoming` is answered as a
  client error before dispatch instead of a server error. `HEAD` on the
  one-time read routes (v2 and v3 `secret` and `receipt` show, guest routes
  included) answers `405` with an `Allow` header instead of consuming the
  secret; `OPTIONS /secret/generate` and `OPTIONS /secret/conceal` answer
  `204` without running creation logic. Secret creation commits the secret,
  its receipt and their registrations in one datastore transaction. PASETO
  v4.public bearer tokens for the v3 API are off by default
  (`PASETO_ENABLED`, `auth.yaml` `paseto.enabled`); a deployment that leaves
  them off is unchanged. With them on, rotating an API key
  (`POST /api/account/apitoken`, `bin/ots apitoken`) retires every bearer
  token issued before the rotation without signing the browser session out,
  the signing key derives from `SECRET`, and `SECRET_PREVIOUS` entries keep
  verifying tokens signed before a rotation. Details:
  `docs/authentication/api-bearer-tokens.md` and the two #4871 fragments.
- In simple mode, a redeemed welcome link now applies a deferred federated
  subscription (#4914), but only for links sent after the upgrade. A link
  sent before it verifies the account and claims nothing for up to its 24
  days; an account in that state needs `bin/ots customers verify EMAIL`.
- With the OAuth IdP on, `email_verified` is true only when the Rodauth row
  is Verified and the Customer's `verified_by` is `email`, `colonel_admin`
  or `cli_provision` (#4917). That excludes `invite_token`, which
  `mailbox_verified?` otherwise accepts. Accounts stamped `sso`, `legacy`
  or blank, `autoverify`, `stripe_payment` or `invite_token` now get
  `false`. `bin/ots customers verify EMAIL` restamps all of these except
  `invite_token` as `cli_provision`, which fixes them. It keeps an
  `invite_token` stamp, so an invite account needs `unverify` and then
  `verify`. Do not do that for an account with a system role: `unverify`
  removes its role eligibility until `verify` runs, and refuses the last
  colonel.
- Full mode runs auth migrations 012 to 015 at boot (012 to 014 are the OAuth
  tables, 015 is #4744's) whether or not `AUTH_OAUTH_ENABLED` is set.
- ADR-051 expand step (#4744). Migration 015 adds `accounts.login`,
  `email_verified_at`, `email_verified_by` and `email_verification_hold`;
  all are nullable and sign-in does not read them. After deploying, run
  `bin/ots customers backfill-logins` (a dry run by default, then for real),
  then `bin/ots customers doctor --all`, which reports rows with no login, a login
  that disagrees with the Customer, or SQL verification that disagrees with
  the Customer's mailbox proof. Later ADR-051 steps are gated on the
  backfill. A confirmed self-service email change now records mailbox proof
  (`verified_by` `email`) for the new address in both stores, also for an
  account verified by an IdP, a payment, autoverify or a legacy stamp, which
  then meets the mailbox-proof requirement for system roles and for applying
  a deferred federated subscription (approved, §5). A release without migration
  015 refuses to start in full mode against a database that has applied it.
- Client IP (otto 2.13, #4922). With `site.network.trusted_proxy` in
  `filter` mode, the client IP is read from `X-Forwarded-For` from the right,
  skipping trusted hops. Every proxy with a public address (a CDN edge, a load
  balancer) must be listed in `trusted_proxy.cidrs` (`TRUSTED_PROXY_CIDRS`);
  otherwise that hop becomes the client IP for every request through it, and
  per-IP rate limits and bans apply to all of its traffic together. Where the
  clients have private addresses (a LAN, a VPN), the edge must overwrite
  `X-Forwarded-For` rather than append to it. A proxy that writes `unknown`
  or an empty entry leaves the request with no client IP: the admin network
  gate denies it, and per-IP rate limits charge it to one shared
  `no-client-ip` bucket. Details: `docs/deployment/trusted-proxies.md`,
  "Client IP resolution". Check this before upgrading.
- Referrer-Policy is `strict-origin` on every response and document. Fixes the
  403 on the SSO form POST that `no-referrer` produced.
- API: burn requires `"continue": true` and answers 422 without it (#4879); a
  JSON body no longer overrides a path identifier (otto 2.12, on `main`
  since #4871). It still beats query parameters and still reaches handlers
  on GET, because `Rack::Parser` publishes it as the form body. The public API quick start needs
  updating.
- Rollback in full mode is not a tag swap (§5): migrate the auth schema down
  to 11 with the 0.27.0 files first, which drops the OAuth tables and 015's
  columns and keeps accounts. After upgrading again, run
  `bin/ots customers backfill-logins` again: `login` comes back empty.
- `bin/ots domains create` loses `--cert` and `--no-cert`; the provider
  virtual host is created at verification (#4800).
- The bundle includes a git-sourced gem (rodauth-oauth fork at a pinned SHA).
  The image build already installs git; anyone vendoring the bundle offline
  needs that checkout.
- New keys, all off or dev-only by default: `AUTH_OAUTH_ENABLED`,
