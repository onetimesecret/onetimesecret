Added
-----

- (`#3989 <https://github.com/onetimesecret/onetimesecret/issues/3989>`_)
  Sign-in surfaces now show the country a session came from instead of an IP
  address. Otto resolves an ISO 3166-1 alpha-2 country code per request into
  ``env['otto.privacy.geo_country']``, and four surfaces consume it: the
  new-sign-in and MFA alert emails, the Colonel per-customer session sidecar,
  the global Colonel sessions console, and — opt-in only, see below — the
  organization Secret Activity trail.

  Country is deliberately the finest granularity available anywhere in this
  work. It is resolved either from a CDN header trusted only when the request
  demonstrably arrived through a configured proxy, or from a local MaxMind
  country database looked up on the **already-masked** address. Neither path
  receives or reconstructs a raw IP, so this does not loosen the existing
  ``/24`` (IPv4) and ``/48`` (IPv6) masking. When no country can be resolved
  Otto emits an explicit unknown sentinel rather than a guess, and every
  surface renders that as "Unknown" — it is never stored or displayed as
  though it were a country.

  Operator note: nothing is required to get country from a CDN, but the trust
  model matters. Vendor geo headers (Cloudflare ``CF-IPCountry`` and friends)
  are honored **only** in filter mode with ``TRUSTED_PROXY_ENABLED=true`` and
  the CDN's ranges listed in ``TRUSTED_PROXY_CIDRS``. Out of the box, and in
  depth mode, header geo is not trusted and country resolves to unknown.
  Depth-mode and direct-connect deployments should set ``GEO_DB_PATH`` to a
  ``.mmdb`` country database instead; ``GEO_HEADER`` is ignored there, because
  combining it with depth mode is a boot-time conflict in Otto. A bad database
  path fails at boot rather than per request.

  On the organization Secret Activity trail the country attribute is gated
  behind ``SECRET_ACTIVITY_GEO_COUNTRY_ENABLED`` and defaults to **off** — the
  inverse of its sibling flags. Org-tier exposure of members' geolocation is
  an open legal-review question (ADR-021), so with the flag off the attribute
  is never captured, never stored, and the column does not render. Do not
  enable it without that review.

Fixed
-----

- (`#3989 <https://github.com/onetimesecret/onetimesecret/issues/3989>`_)
  The account "active sessions" list showed no IP address, browser or country
  for any session. The list joins Rodauth's session rows to the metadata that
  holds those details, but it joined on the wrong value: Rodauth mints its own
  opaque token per session and stores a digest of *that*, never of the session
  cookie's id. The two digests are of different inputs, so no row ever
  matched. The failure was invisible because the timestamps have an
  independent fallback and kept rendering normally.

  The session metadata now carries the digest Rodauth actually stores,
  computed at sign-in time where the auth layer's key material is available.
  The raw token is deliberately not carried — the metadata record is not
  encrypted at rest, and Rodauth itself keeps only the digest — and the new
  value is an internal join key that is not exposed through the record's
  serialization allow-list.

  Operator note: sessions that already exist at deploy time have no join key
  until their next sign-in, so they continue to list without those details.
  The list fills in as users re-authenticate; no migration or backfill is
  needed.

Changed
-------

- (`#3989 <https://github.com/onetimesecret/onetimesecret/issues/3989>`_)
  The new-sign-in alert email no longer has an optional ``ip_address`` field.
  No caller ever populated it, and removing it makes the privacy property
  structural: the sign-in origin travels only through the location line, which
  cannot carry an unmasked address. Existing alerts are unaffected — the field
  never appeared in a delivered email.

Documentation
-------------

- (`#3989 <https://github.com/onetimesecret/onetimesecret/issues/3989>`_)
  Recorded the precision-profile evaluation this work called for. The verdict
  is keep-current: country resolution is orthogonal to IP masking, so the
  ``/24``–``/48`` posture needs no change, and policy code that genuinely
  needs full precision should use Otto's IP-match capability rather than a
  looser mask.

  Also reconciled the design records with what shipped. ADR-022 now documents
  the country attribute alongside the three reduced network attributes it
  originally specified, including why country is validated rather than masked
  and why lifecycle events legitimately carry no network context at all.
  ADR-021's open question on org-tier geolocation is marked as blocking the
  default-off flag above. Several Colonel session specs still justified
  deferring geo on the grounds that a masked prefix cannot be geo-located;
  that reasoning no longer applies to country and has been corrected, while
  the same reasoning still correctly rules out ASN and device fingerprinting.
